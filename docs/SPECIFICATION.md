# Спецификация v2 (ТЗ): движок KLAMMER — автоматическое моделирование НВФ в Revit 2024

**Статус:** v2, заменяет спецификацию v1 целиком. Аргументация и обоснование решений — в
`KLAMMER_ENGINE_grill_v2.md` (там — «почему», здесь — «что именно»). При расхождении
документов приоритет у спецификации: она — контракт.

**Ключевое решение v2:** текущее ядро решает только Tier 0 (голый прямоугольник без проёмов),
и его модель данных (`Substrate = Width×Height`, раскладки как декартовы произведения)
активно препятствует расширению. v2 — **не рефакторинг, а рестарт контрактов данных Core**
с сохранением двух верных принципов v1: чистое детерминированное Core без Revit-типов и
тонкий адаптер; детерминизм и идемпотентность как тестируемые свойства.

---

## 1. Цель и продуктовая рамка

Движок автоматически моделирует навесные вентилируемые фасады (НВФ) в Autodesk Revit 2024:
раскладка подоблицовочной конструкции (ПОК), облицовки, слоёв пирога, доборных и узловых
элементов — и выпускает **три артефакта**:

1. **Модель** — редактируемая, ассоциативная (повторный расчёт не разрушает оформление —
   см. §8), элементы несут shared-параметры для расписаний.
2. **Ведомость (BOM)** — **количественная**: позиции по SKU и зонам, количества, длины,
   площади. *Не ценовая*: цены живут в ERP производителя; ценовое соединение — задача
   покупателя, не движка.
3. **Паспорт расчёта** — воспроизводимый байт-в-байт документ с provenance каждого элемента
   (правило, версия, входная грань, параметры, ссылка на норму, цепочка допущений, хэш
   входа). Паспорт даёт **аудируемость, а не юридическую силу**: юридический статус возникает
   только под подписью лицензированного инженера в составе проектной документации.

Пользователь — инженер-фасадчик, **не** специалист по вычислительному проектированию.

**Границы честности (печатаются на первой странице паспорта):**
- «Соответствие нормам» = конформность **параметрическим ограничениям** СП/ГОСТ (шаги,
  отступы, минимальные размеры), **не** поверочный расчёт нагрузок.
- Ведомость количественная, без цен.
- Все допущения перечислены явно; молчаливых решений нет.

## 2. Термины

| Термин | Значение |
|---|---|
| ПОК | Подоблицовочная конструкция: кронштейны, направляющие, крепёж |
| Tier (T0–T5) | Уровень геометрической сложности здания (см. §3) |
| Регион | Плоская область стены: внешний контур + отверстия (проёмы) |
| Курс | Горизонтальный ряд облицовки, привязанный к датуму |
| Датум | Опорная линия/уровень раскладки (глобальный для здания с T2) |
| SKU | Уникальный типоразмер элемента (панель, кронштейн, профиль) |
| Доборный элемент | Резаный/краевой элемент облицовки |
| Sliver | Недопустимо узкий обрезок панели — запрещённый выход |
| Provenance | Трассировка происхождения элемента: правило + норма + допущения |

## 3. Уровни сложности и область версии

| Tier | Охват | Статус в v2 |
|---|---|---|
| T0 | Плоский прямоугольник | Реализовано (v1), переезжает на новые контракты |
| **T1** | Реальный контур + проёмы | **Область Phase 1 — предмет этой спецификации** |
| T2 | Мультигрань + углы | Контракты закладываются сейчас (§4.2), реализация — Phase 2 |
| T3 | Полное здание (парапеты, термика, ветровые зоны) | Схема данных закладывается (§4.4), реализация — Phase 3 |
| T4 | Наклонные/гранёные/цилиндрические | Интерфейс `ISurface` зарезервирован, реализация — Phase 4 |
| T5 | Свободная форма | Вне продукта — не обещается |

**Phase 1 (единственный календарь): T1 × керамогранит на видимом кляммере**
(рядовой/стартовый/концевой). Скрытое крепление (аграфы/пропил в торце) в Phase 1 **не
реализуется** — оно входит в бумажную валидацию схемы третьим кислотным тестом. Схема
`SystemDefinition` обязана на уровне дизайна выдерживать проверку против металлокассеты
(модуль «под заказ»), планкена (курсы без вертикальной сетки) и скрытого кляммера (смена
стратегии крепления) — чтобы реализация видимого кляммера не вшила предположения
каталожного модуля. Реализация этих систем — Phase 2+.

## 4. Доменная модель Core v2 (`RevitNvf.Core`, без Revit-типов)

Все координаты — **мм/СИ**; направление обхода внешнего контура — против часовой стрелки,
отверстий — по часовой; координаты привязаны к фиксированной сетке **0,1 µm** (снап при
построении) — булевы операции над полигонами точные и детерминированные. Единая политика
допусков — тип `Tol` (один на всё Core; локальные эпсилоны запрещены).

Булевы операции выполняет **Clipper2** (int64-координаты; множитель 10⁴ на мм даёт
сетку 0,1 µm) за тонкой обёрткой `Ring`/`PlanarRegion` — прямые вызовы Clipper2 вне
обёртки запрещены. Clipper2 — единственная внешняя зависимость `RevitNvf.Core`.

### 4.1 Геометрия и подложка

| Тип | Контракт |
|---|---|
| `Point2d` | Существует (v1) — сохраняется как есть |
| `Vector2d`, `Point3d`, `Vector3d` | Новые примитивы (immutable struct) |
| `Ring` | Замкнутый полигон: `IReadOnlyList<Point2d>`, снап к сетке, без самопересечений (валидируется при создании) |
| `PlanarRegion` | Внешний `Ring` + `IReadOnlyList<Ring>` отверстий + `FaceFrame`. **Заменяет `Substrate`.** |
| `FaceFrame` | Мировая привязка грани: `Origin` (Point3d) + оси U/V, где **V сонаправлена гравитационной вертикали** (не UV грани Revit!) + нормаль |
| `BuildingEnvelope` | `IReadOnlyList<PlanarRegion>` + `CornerEdge[]` (полурёбра смежности с классификацией двугранного угла: ExternalL / Internal / Coplanar / Parapet / Plinth / Expansion) + `LevelBand[]` (общие датумы уровней). В Phase 1 населяется одной гранью; контракт обязан существовать с первого дня — курсы, стыки и зоны ссылаются на датумы здания, не на грань |
| `ISurface` | Planar / Cylindrical / Conical как аналитические чистые структуры; freeform приходит фасетированным от адаптера под явной `FacetingPolicy { MaxChordMm, MaxWarpDeg, FlatFacet\|ColdBend\|Reject }`. В Phase 1 — только Planar |

### 4.2 Система как данные

| Тип | Контракт |
|---|---|
| `SystemDefinition` | Декларативное описание фасадной системы (замена `FacadeSystem` + `Cladding` + `FacadePreset`): идентификатор + версия; **авторитет модуля** (каталожный / под заказ); **авторитет шва** (параметрический / фиксированный оснасткой); политика реза (свободный / только завод / перезаказ); ссылки на стратегии; ограничения как данные `{min, max, default, normRef}` |
| `SubstructureSpec` | Шаги/отступы кронштейнов и направляющих как ограничения; `WindZone[]` — **декларативные предикаты** (CornerStrip(w) / ParapetBand(h) / HeightAbove(z) / OpeningMargin(d)), вычисляемые в маски по графу оболочки. В Phase 1 обязателен только OpeningMargin; схема — полная |
| `IPanelizationStrategy` | Сетка = **список курсов** (не прямоугольная матрица!) + `LayoutDatum { Anchor, BondPattern, CourseSource }`. Перевязка = фазовый сдвиг по рядам; курсы-от-уровней бьются по перекрытиям. Кислотный тест схемы: планкен («только курсы», без вертикальной сетки) выражается без хака |
| `ICornerStrategy` | Открытый шов + профиль / гнутый SKU с развёрткой / запил / вендорский экструзионный элемент. Phase 1: заглушка (одна грань) |
| `IAttachmentStrategy` | **Крепление реляционно**: сущности-связи панель↔направляющая (рядовой кляммер принадлежит двум курсам; кассетный замок диктует порядок монтажа; заклёпочные схемы с одной неподвижной точкой). Даёт `PreferredGuideStep`. Кислотный тест схемы: скрытое крепление (аграфы/пропил) выражается сменой стратегии и данными, не правкой схемы |

Сериализация `SystemDefinition` — версионируемый JSON (в v1 сериализации нет вообще —
вводится здесь); формат — деталь реализации, стабильность ключей — контракт.

Первый документ системы — **генерик** «керамогранит на видимом кляммере» с параметрами
из СП 426 / ГОСТ Р 58154-55 и типовых альбомов (каждое число с `normRef`). Вендорские
каталоги подключаются позже как JSON-документы той же схемы, без изменений кода.

### 4.3 Результат и идентичность

| Тип | Контракт |
|---|---|
| `GeometryInput` | Вход конвейера: грани/рёбра/уровни + `SystemDefinition` + параметры запуска. Сериализуем в JSON (golden-фикстуры, §11) |
| `LayoutResult` | Выход: кронштейны; сегменты направляющих (со сплайсами и признаком фикс/скольжение — поле есть с Phase 1, солвер — Phase 3); ячейки панелей с **контуром-полигоном** (`Ring`), классификацией и SKU; откосы/отливы/доборы; сущности крепления; `BillOfMaterials` |
| `PanelKey` и др. ключи | **Стабильный ключ каждого выходного элемента**: `{ FaceId, CourseIndex, PositionIndex, SystemId }` — относительно датумов, не абсолютных координат. Сдвиг окна меняет ключи только затронутых ячеек. Обязателен на каждом элементе `LayoutResult` с Phase 1 — ретрофит невозможен |
| `Provenance` | На каждом элементе: `RuleId` + версия правила + входная грань + параметры + `NormRef` + предки-допущения + хэш входа |
| `BillOfMaterials` | Позиции по SKU × зона с количеством/длиной/площадью + provenance. Замена `TakeoffReport` |

### 4.4 Классификация ячеек панелизации

`Full / CutByOpening / CutByEdge / Reveal / CornerFiller / Sliver`.
**Инвариант: `Sliver` никогда не попадает в выход** — поглощается соседом или конвертируется
в добор согласно `ResolutionPolicy { MinPanelFraction }`. SKU в Phase 1 — детерминированное
квантование в корзины по 5 мм + подсчёт; глобальная оптимизация раскроя — отложенный
сменный потребитель стадии 7.

## 5. Конвейер — семь чистых стадий

```
GeometryInput → [1] SubstrateExtraction → [2] RegionModel → [3] SubstructureLayout
→ [4] Panelization → [5] CornerOpeningResolve → [6] ThermalWindAssign → [7] Takeoff
→ LayoutResult
```

- Каждая стадия — чистая функция над неизменяемыми DTO; независимо golden-тестируема и
  заменяема. Внутри конвейера нет Revit-типов, нет I/O, нет случайности, нет системного
  времени.
- Стадия 1 живёт в адаптере (единственная, видящая Revit), выдаёт `GeometryInput`.
- Стадия 5 в Phase 1 решает **проёмы** (углы — Phase 2): генерация откосов/отливов/перемычек
  с глубиной, выведенной из `LayerStackup`; притяжка швов к откосам.
- Стадия 6 в Phase 1 — сквозная передача с заполнением полей (термосолвер — Phase 3);
  поля в `LayoutResult` существуют с первого дня.

## 6. Функциональные требования Phase 1

Каждое требование тестируемо; «Адаптер» = `RevitNvf.Revit`, остальное — Core.

**Извлечение подложки (адаптер) — правка ошибки корректности №1:**
- **FR-1.** Подложка строится из **реальных `EdgeLoops`** грани — никогда из
  `GetBoundingBox()`. Внешний контур и все отверстия переносятся в `PlanarRegion`.
- **FR-2.** `FaceFrame` гравитационно-ориентирован: V — мировая вертикаль в плоскости грани
  (UV-базис грани Revit не используется как система координат раскладки).
- **FR-3.** Копланарные смежные грани (разрезанная стена) объединяются в один регион до
  раскладки.
- **FR-4.** Каталог грязных моделей F1–F10 (§9.3): каждый случай — детект + действие
  (починить / спросить / отказать) + регрессионная `.rvt`-фикстура. Запись каталога без
  фикстуры считается нереализованной.

**Раскладка ПОК:**
- **FR-5.** Зоны исключения анкеров вокруг проёмов + минимальные краевые расстояния
  (значения — данные `SystemDefinition` с `normRef`; ориентир ~100 мм).
- **FR-6.** Уплотнение кронштейнов по откосам и перемычкам (jamb/lintel densification).
- **FR-7.** Направляющие разрезаются на сегменты над/под проёмами; каждый сегмент несёт
  поля сплайса и фикс/скольжения.

**Панелизация:**
- **FR-8.** Каждая номинальная ячейка сетки полигонально подрезается по контуру и проёмам;
  результат классифицируется по §4.4.
- **FR-9.** Инвариант «ноль sliver'ов» соблюдается на любом входе.
- **FR-10.** Швы притягиваются к откосам проёмов (joint-to-jamb snapping) в пределах
  допуска из `SystemDefinition`.
- **FR-11.** Генерация узлов проёма: откос/отлив/перемычка с глубиной из `LayerStackup`.
  Узлы материализуются в Revit **полной геометрией** (§9.2) со стабильными ключами —
  не только позициями BOM.

**Выход:**
- **FR-12.** Каждый элемент `LayoutResult` несёт стабильный ключ (§4.3) и `Provenance`.
- **FR-13.** `BillOfMaterials`: позиции по SKU × зона; суммы сходятся с геометрией
  (сохранение площади: панели + швы + проёмы = площадь региона).
- **FR-14.** Валидация (§7) прогоняется всегда; выход либо чист, либо содержит явные
  нарушения — **тихих** нарушений не существует.

## 7. Валидация и нормы

- Ограничения СП 426.1325800.2020 / ГОСТ Р 58154-2018 / ГОСТ Р 58155-2018 / СП 50.13330
  кодируются как **данные** `{параметр, min/max, normRef}` внутри `SystemDefinition` /
  `SubstructureSpec` — не как ветвления в коде.
- Слой валидации **падает громко**: правдоподобно-неверный выход (анкер в шов кладки,
  20-мм обрезок, недоуплотнение в ветровой зоне) — это отказ или флаг, никогда не молчаливый
  рендер.
- Phase 1 минимум: минимальная ширина панели; краевые расстояния анкеров; границы шагов
  ПОК; зоны исключения у проёмов. Термические пробеги и ветровые плотности — поля схемы
  сейчас, проверки — Phase 3.
- Каждое нарушение: `RuleId`, `NormRef`, элемент(ы), фактическое/допустимое значение,
  предлагаемое исправление. Панель нарушений группирует до ≤5 групп.

## 8. Ассоциативность (D1) — архитектурный инвариант с Phase 1

1. **Стабильные ключи** на всех элементах (§4.3).
2. **`MaterializationRecord`** в Extensible Storage документа: доменный ключ → `UniqueId`
   (никогда `ElementId` — он недолговечен) + `OverrideFlags` + `InputHash`. Идентичный вход
   ⇒ истинный no-op (проверяется по хэшу до любых изменений).
3. **Diff-apply**: Added / Removed / Changed / Unchanged в одном `TransactionGroup`;
   Unchanged-элементы **не трогаются** — их теги, размеры, переопределения живут.
4. Ручные переопределения отслеживаются на **гранулярности ключа** (заменить/сохранить);
   конфликты флагуются, не затираются. Трёхстороннего слияния свободной геометрии нет
   никогда.
5. **Элементы архитектора неприкосновенны** — инвариант, не настройка.

## 9. Адаптер Revit (`RevitNvf.Revit`)

### 9.1 Извлечение
FR-1…FR-4; мм↔футы только на границе (`UnitsConvert`); выбор пользователя → `GeometryInput`.

### 9.2 Материализация (масштаб 20–60k элементов)
- Резаные/непрямоугольные панели → **DirectShape** (солиды собираются вне транзакции);
  повторяемые прямоугольные → параметрический `FamilyInstance`; кронштейны/направляющие →
  точечно размещаемые `FamilyInstance`. Криволинейные (T4) → адаптивные компоненты.
- **Никакого face-hosting** — хостинг ломает diff-движок и рассыпается при правке хоста.
  Размещение принадлежит движку.
- Пакетно: **ноль `Regenerate` в циклах** (один на коммит); `FamilySymbol` активируется
  один раз; транзакции по классам элементов внутри одного `TransactionGroup`; крепёж
  **считается, не инстанцируется**.
- Shared-параметры (`NVF_System`, `NVF_PanelSku`, `NVF_BracketType`, `NVF_FixedOrSliding`,
  `NVF_WindZone`, ключ, хэш) биндятся при старте → расписания Revit сходятся с
  `BillOfMaterials` по построению.

### 9.3 Каталог грязных моделей (детект обязателен в Phase 1)
F1 стена из кусков → авто-слияние (FR-3) · F2 связанная модель → читать read-only, размещать
в хосте · F3 проёмы-войды → пакетное подтверждение · F4 не-вертикаль: ≤0,5° проецировать /
0,5–3° спросить / >3° отказ · F5 свесы/русты → поглотить или спросить · F6 многослойные
stacked-стены → разбивка по поясам · F7 витраж как подложка → отказ + узел примыкания ·
F8 масса/DirectShape → отказ → путь аудита · F9 зеркальные семейства → истина = вырез стены ·
F10 нет датума уровней → единственный неустранимый вопрос.

## 10. Интейк и «1 клик»

- **Формула: 1 намерение + K подтверждений + 0 сюрпризов.** K измеряется и показывается;
  цель ≤5 на фасад; 1 обязательное = датум раскладки. Первый клик всегда даёт завершённый
  артефакт: черновой фасад + BOM + паспорт, **или** аудит (площади, оценка на м²,
  конкретный рецепт исправления).
- **Детерминированный путь первичен и полон без LLM**: значения по умолчанию + явные
  диалоги. Детекторы F1–F10 — детерминированный код.
- LLM-слой (после Phase 1, опционально): **переводит, не измеряет**. Жёсткое правило: LLM
  никогда не порождает координату, размер или количество — только классифицирует
  неоднозначности, группирует вопросы, формулирует на языке инженера. Доверие = **ярус
  provenance** (зелёный авто / жёлтый допущение / красный отказ), не самооценка модели.
  Превышение бюджета вопросов → жёлтое допущение в паспорте, никогда молча.
- Вход конвейера — Revit-геометрия. Интейк DWG/PDF **не является стадией движка** (это
  коммерческий процесс подготовки подложки).

## 11. Нефункциональные требования

- **Детерминизм (ворота CI):** два прогона → байт-идентичный `LayoutResult`; перестановка
  порядка входных граней → идентичный результат; паспорт воспроизводим байт-в-байт.
- **Идемпотентность:** повторный прогон на неизменном входе — no-op по `InputHash` (ни
  одного изменённого элемента в документе).
- **Производительность (ориентиры для калибровки на первом бенчмарке, не текущие
  измерения):** пересчёт после правки <5 с на фасад 500 м², <30 с на здание; полная
  генерация ~5000 м² <3 мин включая материализацию.
- **Тестируемость (кросс-платформенно, Linux CI, без Revit):**
  - *Golden buildings*: рукописные JSON-фикстуры `GeometryInput` (tier × система) +
    канонизированные snapshot-тесты.
  - *Инварианты свойств* (property-based): сохранение площади; отсутствие пересечений;
    каждый кронштейн на направляющей; ноль sliver'ов; (с Phase 3) ровно одна неподвижная
    точка на пробег.
  - *Метаморфические тесты*: сдвиг окна ±ε → меняются только локальные ключи (ограничивает
    радиус поражения ассоциативности); масштабирование грани → инвариант числа SKU.
  - Windows-smoke (ручной/nightly): материализация golden-фикстуры в документ; счётчики
    элементов == BOM; итоги расписаний == takeoff.
- **Единицы:** Core — мм/СИ; футы только в адаптере.
- Существующая дисциплина v1 (чистые функции, тесты идемпотентности) сохраняется и
  распространяется на все новые стадии.

## 12. Критерии приёмки Phase 1

Срез бенчмарка «T1 × керамогранит (кляммер)» на golden-зданиях:

| Критерий | Порог |
|---|---|
| Конформность нормам (параметрические ограничения) | 100% элементов в допуске, 0 нарушений на ≥500 элементов |
| Коллизии (слои пирога, ПОК, проёмы) | 0 |
| Дисциплина минимальной ширины панели | ≥98% панелей ≥ min; остальное — только флагованные доборы |
| Sliver'ы в выходе | 0 (инвариант, не порог) |
| Точность BOM против golden | ≥99% по количеству/типу |
| Пересчёт после сдвига окна | Меняются только затронутые ключи; теги/размеры нетронутых элементов живы |
| Детерминизм | Байт-идентичность двух прогонов; инвариантность к порядку граней |
| Ручные правки | ≤1 на 100 м² |

## 13. Вне области v2 (Phase 1)

Углы/мультигрань (T2), термо- и ветро-солверы (T3), наклонные/криволинейные (T4; >3° —
красная зона → аудит), свободная форма (T5 — не обещается); поверочный расчёт нагрузок
(только параметры норм); автоподбор фасадной системы (предзаполнение — инженер нажимает
кнопку); генеративный/стохастический поиск раскладки (детерминизм — фича, на которой стоит
D1); face-hosted размещение (навсегда); интейк DWG/PDF; цены в ведомости; LLM как
зависимость чего-либо.

## 14. Миграция от текущего кода

Фактическое состояние (инвентаризация 2026-07-12): Core 18 файлов / ~720 LOC, 32 тестовых
метода (36 кейсов с учётом Theory), сериализации нет, все типы Tier 0.

| Сейчас | Судьба |
|---|---|
| `Geometry/Point2d.cs` | **Живёт** без изменений |
| `Layout/GridAxis.cs` | **Живёт** как внутреннее ядро генерации осей курсов |
| `Layout/LayerStackup.cs`, `Model/PieLayers.cs`, `Model/Layer.cs` | **Живут**; `LayerStackup` дополнительно питает глубину откосов (FR-11) |
| `Model/Substrate.cs` (W×H) | **Заменяется** `PlanarRegion` + `BuildingEnvelope` (+ `ISurface`) |
| `Model/FacadeSystem.cs`, `Model/Cladding.cs`, `Model/FacadePreset.cs` | **Заменяются** `SystemDefinition` + `SubstructureSpec`; пресеты становятся JSON-документами системы |
| `Layout/BracketLayout.cs`, `Layout/GuideLayout.cs` | **Заменяются** стадией 3 (SubstructureLayout) с зонами исключения и сегментацией |
| `Layout/PanelLayout.cs` | Внутренний `AxisCells` **живёт** как кернел полосы; публичный API **заменяется** стратегийной opening-aware панелизацией |
| `Reporting/FacadeTakeoff.cs`, `TakeoffReport.cs` | **Заменяются** `BillOfMaterials` (SKU × зона × provenance) |
| `Geometry/PlanarFaceSubstrate.cs` (UV-bbox — долг корректности №1) | **Заменяется** извлечением реальных `EdgeLoops` + отверстий + гравитационного `FaceFrame` + объединения копланарных граней (FR-1…FR-3) |
| Команды `Place*Command` (model curves, TaskDialog) | **Заменяются** diff-материализатором (§9.2); диалоги — панелью результатов/нарушений |
| `RevitNvf.UI` (панель параметров) | **Живёт**; источником параметров становится `SystemDefinition`-документ вместо ручных полей |
| Тесты v1 (32 метода) | Тесты `GridAxis`/`LayerStackup`/`Point2d` живут; остальные переписываются против новых контрактов + добавляются ворота §11 |

**Стратегия миграции:** Core v2 строится **рядом** с v1 (новые типы в новых файлах);
v1-типы и адаптер остаются нетронутыми и рабочими, пока конвейер v2 не пройдёт
golden-тесты и ворота §11 (адаптер не собирается в облаке — ломать его до готовности
замены значит жить со скрыто сломанной сборкой). Затем одним шагом (Windows-сессия)
адаптер переписывается на контракты v2, а v1-типы и старые команды удаляются целиком.
Постадийной замены с починкой адаптера после каждого типа нет.

Порядок работ и декомпозиция на задачи — **`docs/ROADMAP.md` (v2)**: вехи A–D + трек
де-рисков E, с целями G1–G6 и критериями приёмки на каждом шаге.
